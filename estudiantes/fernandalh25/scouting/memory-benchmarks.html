How agent-memory benchmarks work, and how they compare

Research summary, 17 Nov 2026. Model-neutral by design: it describes what each benchmark measures and how it scores. It reports no vendor or model leaderboard numbers.

Scope note. "Harness memory" is ambiguous. I read it as: benchmarks that test whether an LLM agent, together with its memory layer (the surrounding code that stores and retrieves information), can retain and use information across long interactions. Most of the field is chat-history based. Only a few newer benchmarks test memory inside agentic tasks. If you meant something narrower, such as coding-agent memory files, only the last two rows of the table are relevant.

1. The common mechanism

Almost every benchmark follows one loop. They differ in what goes into each stage.

1. HistoryA long, timestamped conversation or task stream is built, usually by an LLM pipeline plus human checks.
2. IngestThe system under test reads the history. Some benchmarks feed it incrementally, in chunks.
3. Memory layerThe system stores raw text, summaries, extracted facts, or a graph. Or it stores nothing and keeps the full context.
4. QuestionA question is asked later whose answer depends on earlier content.
5. AnswerA "reader" model answers from whatever the memory layer returns.
6. ScoreAn F1 or exact-match metric, or an LLM judge, compares the answer to a gold answer.

This loop shows what is compared. The thing under test is the whole pipeline (memory layer, reader model and judge), not memory in isolation. Typical comparisons:

  • Memory systems against each other (extraction, summaries, graphs), holding the reader model fixed.
  • Memory systems against baselines: full-context ("put everything in the prompt") and plain retrieval (RAG). Those baselines show whether a memory layer adds anything.
  • Abilities within one system, such as recall, temporal reasoning, updating facts and abstaining when the answer is not in memory.
  • Scale: how accuracy degrades as the history grows from thousands to millions of tokens.

3. Comparison along the axes that matter

What is being tested

  • Recall and QA over a history (LoCoMo, LongMemEval, BEAM). This is the dominant style and is easy to automate. LongMemEval is the one that most explicitly separates knowledge updates and abstention.
  • Memory as a learning or maintenance skill (MemoryAgentBench). It asks whether the agent can learn new rules at test time and reconcile conflicting facts, in addition to retrieving them.
  • Memory in action (MemoryArena, DreamBench-SWE). Success is measured by task outcome, closest to how an agent harness is used. The MemoryArena authors report that agents that do well on long-context memory benchmarks such as LoCoMo perform poorly in their agentic setting. That is a reported finding, and I have not verified it independently.

Scale

Scale ranges from one short conversation (LoCoMo) to 10M tokens (BEAM). Where the whole history fits in a model's context window, the benchmark partly measures long-context ability rather than memory. Scale therefore changes what a benchmark measures.

Scoring

F1 and exact-match are strict but miss correct paraphrases. LLM judges are flexible but depend on the judge model and prompt. This is the largest source of cross-paper incomparability.

4. Known weaknesses (reported by critics, not all independently verified)

  • LoCoMo size. One critique says conversations run ~16–26K tokens and fit in a modern context window. The paper itself reports ~9K tokens on average. These figures conflict, probably because of different tokenizers or counting methods, and I have not resolved which is right.
  • LoCoMo answer key and judge. One analysis claims about 6.4% of gold answers are wrong and that a lenient judge accepts about 63% of intentionally wrong answers. That claim comes from a third-party blog post. Treat it as a lead to check, not a settled fact.
  • Weak baselines hide the question. A "dump everything into context" baseline is reported to score competitively on LoCoMo and LongMemEval. If so, those benchmarks may not separate memory layers from simply having a long context.
  • No standard protocol. Papers vary the judge, reader model, top-k retrieval and subset of questions. Scores from different papers are generally not comparable.
  • Self-reporting. Many published numbers come from the vendors of the systems being tested, and the same vendor sometimes publishes different numbers for one benchmark. That is a conflict of interest independent of any particular model or product.
  • Coverage gaps. Critics note that chat-history benchmarks rarely test conflicting information streams, behaviour change after mistakes, or months-long histories.

5. Neutral guidance for reading a result

  1. Check which reader model and judge model were used. Different models make scores incomparable.
  2. Check whether a full-context baseline was run on the same data. If not, you cannot tell whether memory helped.
  3. Check history size against the context window. A history that fits tells you less about memory.
  4. Ask who ran the evaluation. Independent or paper-authored runs are weaker evidence of bias than vendor self-reports, but replicate if the decision matters.
  5. Match the benchmark to your use: QA recall (LongMemEval, BEAM), updating and forgetting (MemoryAgentBench), or task outcomes (MemoryArena, DreamBench-SWE).
Limits of this research. I did one search pass per benchmark and read search summaries rather than every paper in full. I did not run any benchmark or check leaderboards, and I found little independent criticism of MemoryAgentBench. DreamBench-SWE is a single-author preprint. Specific numbers marked above come from secondary sources.
